PHASE 1 — Make the core feature actually work (highest priority)
────────────────────────────────────────────────────────
Switch violation extraction from regex-parsing prose to structured output:

1a. In backend/rag/query.py, add a non-streaming analyze function that calls
    Claude with a tool/JSON schema so it returns violations as structured data:
    { criterion, criterion_name, level, line_number, description, fix }.
    For PR diffs, instruct Claude to derive line_number from the @@ hunk headers
    in the patch (the NEW-file line number). Keep the streaming analyze_content
    for the /api/analyze endpoint.
1b. Create backend/rag/parse.py (or similar) as the single home for any shared
    violation-shaping logic, and delete the three copy-pasted regex parsers in
    github.py, scanner.py, and repo_scan.py.
1c. Update /api/github/analyze-pr to use structured output so violations carry
    real line numbers.
1d. Fix /api/github/post-comments to actually post: map line_number to the diff
    correctly, and return which comments failed rather than silently dropping
    them.
1e. Update scanner.py and repo_scan.py to use the structured path too. While in
    scanner.py: strip <script>/<style>/<svg> content and cap the HTML sent to
    Claude; emit progress events ("rendering", "analyzing") so the UI isn't a
    blind spinner; fix the media-type labels (NDJSON everywhere =
    application/x-ndjson).
1f. Raise max_tokens (4096+) and detect stop_reason == "max_tokens".
1g. VERIFY end-to-end: start the backend, hit /api/scan-url against a real page
    (e.g. https://example.com), and confirm structured violations come back.
    For the PR flow, use the test PR (see "WHAT I NEED FROM YOU") and confirm an
    inline comment actually appears on GitHub.
