The headline you cannot use, and why

The README says findings are grounded “in the real WCAG 2.1 specification — not in the model's training memory.” On a 30-case eval that is measurably false in the direction that matters: the model already knows WCAG 2.1. Claude Sonnet 4.5 with no retrieved context at all cited a real, correctly-named, correctly-levelled criterion 100% of the time and caught the seeded violation in 90% of cases. Adding retrieval moved those to 97.1% and 60%.

The mechanism is visible in the numbers. The system prompt tells the model to report only what the provided context supports — but the correct criterion is present in the six chunks it receives only 23.3% of the time, so the instruction mostly suppresses correct findings rather than grounding them.

§1 RAG versus no retrieval

No eval, test set, or manual review existed in the repository — grep for eval/benchmark/baseline across all source returns only prose mentions. One was built for this review: 30 hand-authored snippets, each seeded with a single clear violation, covering 25 distinct success criteria. Both arms use the identical model, system prompt, and report_violations tool schema; the only difference is whether the six retrieved WCAG chunks are prepended.

Citations naming a real WCAG 2.1 criterion

RAG is worse
97.06% with RAG  ·  100% without

33 of 34 RAG citations valid; 46 of 46 no-RAG citations valid.

How
Every emitted criterion was checked against all 78 WCAG 2.1 success criteria parsed straight out of backend/data/wcag21.html. Name and conformance level were checked too — both matched the spec 100% of the time in both arms.
The one miss
SC 3.3.7 “Accessible Authentication” — a WCAG 2.2 criterion, and it came from the retrieval arm. Cause: backend/data/wcag21_quickref.html is the live W3C quickref, which carries 87 criteria including 9 that only exist in 2.2. Retrieval injected out-of-version spec text.
Verify
run_rag_vs_norag.py → score_rag_eval.py; raw per-citation scoring in results_rag_vs_norag.json.

Seeded violation actually caught

RAG is worse
60.0% with RAG  ·  90.0% without

18 of 30 versus 27 of 30. Discordant pairs: 2 caught only with RAG, 11 caught only without.

Significance
McNemar exact two-sided p = 0.022 on 13 discordant pairs. This is not sampling noise at n = 30.
Grounding
Only 32.4% (11 of 34) of RAG-arm citations had their criterion number literally present in the retrieved chunks. The model is answering from parametric knowledge in both arms; retrieval mostly adds a constraint it then obeys too strictly.
Caveat
The no-RAG arm inherits a system prompt written for RAG (“only report violations supported by the provided context”), which is vacuous with no context. That asymmetry favors the no-RAG arm's recall — but it does not explain the valid-citation result, where no-RAG is also ahead.

Read carefully
The false-negative rate is hard: the seeded criterion was either reported or it was not. The false-positive rate is soft — it counts any criterion outside a hand-labelled allow-list, and several “out-of-scope” calls are defensible (flagging 4.1.2 on an unlabelled radio group, for instance). Do not put the FP number on a résumé without that qualifier.

§2 Cost optimisation

Input token counts are exact, from Anthropic's /v1/messages/count_tokens endpoint with the real system prompt and tool schema attached. Priced at the published claude-sonnet-4-5 rate of $3.00 per MTok input and $15.00 per MTok output. Output tokens use the measured mean of 201.2 per call from the §1 run, multiplied by call count — this is the only modelled quantity on the page and it is labelled as such.

Why it works
Each call re-sends the same fixed overhead: system prompt, tool schema, and roughly 3,500 tokens of retrieved WCAG context. Splitting one file into n chunks pays that overhead n times. The saving therefore scales with file size — small files save least.
Chunking baseline
The per-chunk arm uses the project's own ingest settings — SentenceSplitter(chunk_size=512, chunk_overlap=50) — so it is a fair “naive” comparison, not a strawman.

The “re-ranking” step is a no-op, then a lossy truncation

Claim fails
0of 30 queries reordered

And the slice to 6 drops the correct criterion in 10 of 30 further cases.

What the code does
rag/query.py:74 sorts the 15 retrieved nodes by n.score descending, then slices to 6. That is the same cosine score ChromaDB already sorted by — no cross-encoder, no second model, no new signal. Measured across 30 queries the sort changed the order zero times. It is a 3.8 µs no-op.
The real cost
Whether the correct criterion's spec text is present at all: 56.7% at k=15, 23.3% at k=6. The slice throws away the right chunk in 10 of 30 cases — a 33.3 percentage-point loss of retrieval recall, which is the direct cause of the recall gap in §1.
Worth saying
This is the most useful engineering finding here. Passing all 15 chunks through would more than double retrieval recall for roughly 3,500 extra input tokens per call (about $0.01 at Sonnet 4.5 rates).
Verify
run_retrieval_perf.py (rerank_changed_order_vs_chroma) and run_retrieval_recall.py.

Not one test asserts that a given snippet yields a given success criterion. §6 What is safe to write down

Each of these traces to a committed script and a committed JSON result. The wording matters as much as the number — the qualifiers are what make them defensible if someone asks.

  • →Cut per-PR review cost by 98% on a 30-file pull request (measured $0.0178 versus $1.2122) by filtering non-UI files and batching each file into one structured Claude call instead of per-chunk calls — exact token counts via Anthropic's token-counting endpoint. Say 46–86% for the single-file case, and note the saving scales with file size.
  • →Filtered out 73.5% of files before any LLM call across 2,173 tracked files in five open-source repositories (range 52.9–97.8%), via a file-type allow-list plus a UI-markup content check.
  • →Built a 30-case WCAG 2.1 evaluation harness covering 25 distinct success criteria, graded against all 78 criteria parsed from the W3C spec — and used it to show retrieval was reducing recall from 90% to 60% (McNemar p = 0.022), tracing the cause to 23.3% retrieval recall at k=6.
  • →Median 3.2 ms vector search over 650 embedded WCAG passages; retrieval is ~7% of the 4.3 s median end-to-end response, the LLM call is the rest.
  • →43 passing tests, 56% coverage of backend application code across a FastAPI service with 6 endpoints.

Three things to fix before this ships anywhere

Pass all 15 chunks, or re-rank for real. The current slice to 6 is the single largest measured accuracy loss in the pipeline, and it buys 3.8 µs.

Re-index the quickref, or drop it. The file is the live WCAG 2.2 quickref under a 2.1 filename, and it is the demonstrated source of the one out-of-version citation.

Remove “100% findings cited” from the landing page. Nothing measures it, and the nearest real number — 97.1% of RAG-arm citations naming a valid criterion — is not 100%.
